# E2E Gate: Playwright + Firebase Emulator Suite (2026-08-07)

Branch: current working tree (uncommitted facelift work present; this design is independent of it but its selectors must survive it).

## Context & motivation

LeCoursville is Firebase-only (Auth + RTDB + Storage + Hosting, no backend). Deploys are manual via `scripts/deploy.sh` with no pre-deploy verification: `build -> tag -> firebase deploy`. The only e2e assets are a dead Protractor harness (`e2e/`, builder removed from Angular in v16) whose specs log into the REAL dev database with a committed plaintext credential.

Goal: a deterministic, real-browser e2e suite that exercises every feature and blocks the deploy if anything is broken. Runs against the Firebase Emulator Suite (auth, database, storage, hosting) serving the production-optimized bundle, so it is fast, resettable, and touches no real data.

Decisions locked with the user (2026-08-07):
- Gate blocks BOTH prod and dev deploys.
- Gate wired into `scripts/deploy.sh` now (no CI exists; CI can come later without changing the gate).
- Browser matrix: Chromium + WebKit + Firefox.
- Post-deploy smoke layer against live dev hosting: DEFERRED, not in this doc.
- Deploy NEVER proceeds past the gate without an explicit human sign-off; the gate runs before any build/tag/deploy step.
- A failed gate leaves agent-consumable artifacts, and the repair loop is a designed, documented flow.

## Glossary

- Gate: the deploy-blocking command `npm run e2e:gate`.
- Emulators: Firebase Emulator Suite processes for auth/database/storage/hosting, run by `firebase emulators:exec`.
- Seed: `scripts/e2e/seed.mjs`, a zero-dependency Node script that resets and populates the emulators with deterministic data.
- Spec: a Playwright test file under `e2e/specs/`.
- Fail-open: the app treats a missing `features/<id>` record as enabled (see current state).
- Hosting fixtures: small binary files (png/wav/pdf) the seed writes into `dist/lecoursville/assets/e2e-fixtures/` and the app loads from the hosting emulator.

## Goals

- One command (`npm run e2e:gate`) that builds the production-optimized bundle with emulator wiring, boots all four emulators, seeds deterministic data, runs the full Playwright matrix (Chromium, WebKit, Firefox), and fails loudly on any broken feature or console error.
- Block prod AND dev deploys in `scripts/deploy.sh` until the gate is green.
- Force an explicit human sign-off AFTER a green gate and BEFORE any build/tag/deploy step; any deploy action is impossible without it.
- A failed gate writes machine-readable artifacts (`test-results/e2e-results.json`, traces, screenshots, videos) that a fresh agent session can consume to diagnose and fix, with a documented repair loop.
- Exercise every route in `src/app/app-routing.module.ts:31-168` plus the guards: auth, admin, feature-flag, photo-albums, and the unauthenticated public upload.
- Zero network dependence on external hosts (media fixtures served by the emulators themselves).
- Delete the dead Protractor harness and its committed credential.

## Non-goals

- Post-deploy smoke against live `lecoursville-dev` hosting (deferred, separate design).
- CI pipeline setup (GitHub Actions). The gate is CI-ready as a plain command; wiring it in later is a config change only.
- Testing real Firebase console security rules (no rules files in repo; see risks).
- Testing real password-reset email delivery (emulator intercepts; out of scope).
- Cross-browser mobile viewports (one desktop viewport per browser for the gate).
- The gate auto-fixing, auto-approving, or auto-deploying. Repair is an agent loop the user triggers; sign-off is always human.

## Prerequisites

- Node >= 18 (global fetch available).
- `npx playwright install` run once locally to download Chromium/WebKit/Firefox binaries. CI later: `npx playwright install --with-deps`.
- Firebase CLI available as a devDependency (`firebase-tools`) so the gate does not depend on a global install.
- Dev project `lecoursville-dev` referenced by `.firebaserc` (default project) and by `src/environments/environment.ts` firebaseConfig; the storage emulator bucket name comes from that project id.

## Design principles

1. Determinism over speed. Shared RTDB state means tests run serially (`workers: 1`); mutation tests restore state in `afterEach`.
2. Test the prod bundle. `ng build --configuration=e2e` (production optimization + emulator environment) is what the hosting emulator serves.
3. Zero external network. Every URL the app loads in the gate resolves to `localhost` (hosting emulator fixtures or storage emulator).
4. Zero new runtime dependencies. Seed uses Node fetch against emulator REST endpoints; `@playwright/test` and `firebase-tools` are devDependencies only.
5. Resilient selectors. Role/label/text queries first; `data-testid` only where the DOM is ambiguous or dynamic (exact list below).
6. Console-error assertion as a global guard, with a documented allowlist.

### scripts/e2e/seed.mjs (new, zero-dependency Node script)

Runs INSIDE `firebase emulators:exec` (all emulators already up). Idempotent; safe to re-run. Steps in order:

1. Reset RTDB: `DELETE http://localhost:9000/.json` (clears every path; makes every run deterministic).
2. Create auth users. For each of `admin@e2e.local`, `user@e2e.local`, `other@e2e.local` (password `E2e-pass-2026` for all, plus a second `user@e2e.local`-only password variant not needed): `POST http://localhost:9099/identitytoolkit.googleapis.com/v1/accounts:signUp` with `{ email, password, returnSecureToken: true }`. If response is 400 with `EMAIL_EXISTS`, call `POST .../accounts:signInWithPassword` with the same body to obtain the existing `localId`. Collect the three `localId` values.
3. Build the seed tree and `PUT http://localhost:9000/.json` with it. Contents:
   - `users/<localId>` for all three: `{ id: <localId>, name, email, roles: { user: true, admin: true } }` for admin; `{ user: true }` for the other two. Include `dateRegistered` (now - 60d) and `dateLastActive` (now).
   - `features/<id>` for ALL nine ids from `feature-config.ts:10-22`: `people, contacts, calendar, music, videos, photos, enablePhotoAlbums, expressions, chat`. Shape `{ enabled: true, updatedAt: now }` for all EXCEPT `chat` which is `{ enabled: false, updatedAt: now }` (mirrors dev state; drives the feature-disabled test).
   - `promotedRoute`: `{ route: '/calendar', updatedAt: now }` (login lands on /calendar; test asserts it).
   - `contacts`: 3 records per `Contact` shape, `isEditable: true` for the two owned by admin, `false` for one.
   - `people`: 4 records per `Person` shape, with `birthday` / `anniversaryDate` computed RELATIVE TO TODAY (algorithm below) so the current month calendar view shows events, and `clanId` pointing at a seeded clan, `isLiving: true`, `createdAt/updatedAt` set.
   - `families`: 2 records; `clans`: 2 records (one per family color).
   - `photoAlbums`: 2 records (`coverPhotoId` = one seeded photo id).
   - `photos`: 4 records across the 2 albums. Each `url` = `http://127.0.0.1:9199/v0/b/lecoursville-dev.appspot.com/o/photos%2F<albumId>%2Fphoto<N>.png?alt=media` (storage emulator download URL for the fixture uploaded in step 5). `path`/`extension`/`dateAdded`/`albumId` set.
   - `messages`: 3 records per `Message` shape, `messageType: 'message'`, `dateSent` within the app-settings window (`src/environments/app-settings.ts` `messages.includeMessagesFromHowManyMonths`; seed uses now - 1 day), two authored by admin, one by user.
   - `media`: 3 records:
     - audio: `{ title: 'E2E Audio', type: 'audio', format: 'wav', urls: { download: 'http://localhost:5000/assets/e2e-fixtures/fixture.wav', icon: same } }` plus required fields.
     - doc: type `'doc'`, `urls.download` = `http://localhost:5000/assets/e2e-fixtures/fixture.pdf`.
     - video: type `'video'`, `urls.download` = a Google Drive URL string (player shell only; playback not asserted). Mark `isSticky: false`, `isHidden: false`.
   - `addresses`: 2 records per `Address` shape.
   - `calendars`: 1 record `{ id, path, url, year }` (admin calendars page lists it).
   - `userUploads`: 1 pre-seeded record `status: 'approved'`, `url` = `http://localhost:5000/assets/e2e-fixtures/fixture.png`, uploader email `user@e2e.local` (admin uploads page renders it; the public-upload test creates a second 'pending' record through the real UI flow).
4. Write hosting fixtures into `dist/lecoursville/assets/e2e-fixtures/` (created if missing): `fixture.png` (1x1 PNG bytes, base64 embedded), `fixture.wav` (short silence, base64 embedded), `fixture.pdf` (minimal valid single-page PDF, base64 embedded). The hosting emulator serves them at `http://localhost:5000/assets/e2e-fixtures/<file>`.
5. Upload photo fixtures to the storage emulator: `POST http://localhost:9199/v0/b/lecoursville-dev.appspot.com/o?uploadType=media&name=photos%2F<albumId>%2Fphoto<N>.png` with body = the same PNG bytes, `Content-Type: image/png`. Two uploads per album (4 total).
6. `console.log` a short summary: users, nodes seeded, fixtures written, elapsed ms. Exit non-zero on any fetch failure.

Calendar-relative date algorithm (must keep events visible in the current month view; clamp to avoid month/leap-day edge cases):
- Person A birthday: `new Date(now.getFullYear() - 30, now.getMonth(), Math.min(now.getDate(), 28))`.
- Person B birthday: same pattern with `Math.min(now.getDate() + 2, 28)`.
- Person C anniversary: `Math.min(now.getDate() + 1, 28)`.
- Person D birthday: 3 months before today (must NOT appear in the current month; the calendar spec asserts it does not).

## Deploy flow and sign-off (scripts/deploy.sh)

New call order in `main()` (both deploy paths):

- prod: `validate_prod_branch` then `run_e2e_gate` then `build_prod` then `tag_build` then `deploy_prod`.
- dev: `validate_dev_branch` then `run_e2e_gate` then `build_dev` then `deploy_dev`.

The gate therefore runs BEFORE any build/tag/deploy step, and `set -e` means a red gate aborts immediately. No deploy action can happen without passing through `sign_off`.

New functions (exact):

```bash
run_e2e_gate() {
  echo "=== Running e2e gate ==="
  npm run e2e:gate
  local exit_code=$?
  if [ $exit_code -ne 0 ]; then
    echo ""
    echo "E2E gate FAILED. Do not deploy."
    echo "Artifacts for the fix loop: test-results/e2e-results.json (JSON), playwright-report/index.html (HTML), test-results/ (traces, screenshots, videos)."
    echo "Start a session and say: fix the e2e gate. Drive the loop in 'Failure fix loop' below; re-run 'npm run e2e:gate' until green, then deploy again."
    exit $exit_code
  fi
  sign_off
}

sign_off() {
  if [ ! -t 0 ]; then
    if [ "$E2E_APPROVED" = "1" ]; then
      return
    fi
    echo "ERROR: non-interactive shell cannot sign off. Re-run interactively or set E2E_APPROVED=1 to approve the gate result."
    exit 1
  fi
  echo ""
  echo "=== E2E gate PASSED (chromium, webkit, firefox) ==="
  echo "Review the report: open playwright-report/index.html"
  printf 'Type "deploy" to approve and continue, anything else to abort: '
  read -r approval
  if [ "$approval" != "deploy" ]; then
    echo "Deploy aborted by user (gate was green; no deploy action ran)."
    exit 1
  fi
}
```

Rules: the approval word is exactly `deploy`; any other input (including empty) aborts with a clean message. In a non-interactive shell (future CI), sign-off requires `E2E_APPROVED=1` explicitly, so CI cannot silently skip the gate. The `read` prompt is single-shot, not a retry loop: a mistyped word aborts, and the user re-runs the deploy command.

## Failure fix loop (agent procedure, documented for fresh sessions)

When the gate fails, `deploy.sh` prints the artifact paths and aborts. The user then starts (or continues) a session and asks the operator to fix the gate. The operator drives this loop:

1. Read the machine-readable results: `test-results/e2e-results.json` (per-test status, error messages, locations). Read `playwright-report/index.html` for the human view. Open per-test traces in `test-results/` (`.zip`) for interaction replay.
2. Re-run only the failures for a fast diagnosis loop: `npx playwright test --last-failed` (Playwright persists last-run state from the JSON reporter). Diagnose each failure into exactly one bucket:
   - Test bug: bad selector, wrong expectation, timing assumption. Fix the spec file.
   - Seed bug: seeded data does not match what the app actually renders (model drift, missing node). Fix `scripts/e2e/seed.mjs`.
   - App bug: the feature is genuinely broken. This is the gate doing its job; fix the app code (operator routes to `@builder`), not the test.
   - Flake: timing/network nondeterminism. Fix the root cause or the test's wait, never mask with retries.
3. Iterate `--last-failed` until empty, then run the FULL gate (`npm run e2e:gate`, all three browsers, seed reset) because sign-off requires a complete green run, not a partial one.
4. Report to the user: root cause per failure, fix applied, and the full-gate result. Sign-off remains the user's call at deploy time.

Who fixes what: the operator integrates and verifies; `@builder` fixes app/seed code; `@qa-engineer` verifies PASS/FAIL with executed commands; `@adversarial-critic` reviews any fix that changes app behavior before the full gate re-run. A fresh session picks up from step 1 using the artifact paths above, so the loop does not require the original session's context.

## Production risks & mitigations

1. Emulator gate does NOT test production security rules. RTDB/Storage rules live only in the Firebase console; the emulator runs with default allow. Mitigation: this is accepted for now; follow-up (out of scope) is exporting rules into repo (`database.rules.json`, `storage.rules`) so the gate enforces them. Post-deploy smoke (deferred) will catch rule regressions.
2. Google Drive video iframe playback cannot be deterministic. Mitigation: video spec asserts the player shell renders only; playback is not asserted. Documented in the spec file.
3. Google API calls (`environment.googleApiKey`) may hit real network. No seeded feature calls them in the gate; if a spec triggers one, route interception (`page.route`) stubs it.
4. Console-error assertion false positives (analytics, emulator warnings). Mitigation: analytics init disabled in emulator mode (above); allowlist in `e2e/helpers/console.ts` for `[Emulator]` prefixed logs, aborted drive iframe requests, and network `ERR_ABORTED` during teardown.
5. Runtime: 55 specs x 3 browsers serial. Estimate: ~8-11 min per browser (avg ~9s/test: page load + Angular bootstrap + localhost emulator reads; heavy tests are auth login, CRUD forms, photo upload, media playback wait, PDF viewer), so the test matrix is ~25-33 min, plus `ng build --configuration=e2e` (~2 min) and emulator boot + seed (<1 min): **~30-35 min per full gate**. Worst case when the app is badly broken is much longer: each spec is capped by its 60s timeout, so a total failure approaches 55 x 60s per browser; the gate is still correct, just slow, and the fix loop's `--last-failed` iterations are short (~2-4 min each). Mitigation: accepted (user chose the full matrix); `--project=chromium` is ~10-13 min for pre-commit local runs; CI (future) can parallelize with isolated emulator instances + seeds per shard to approach ~10 min.
6. Port collisions with a running `ng serve` (4200) or existing emulators. Mitigation: hosting emulator uses 5000 (not 4200); the gate is a separate shell invocation; document `lsof -i :<port>` if a collision is reported.
7. Seed drift if a model shape changes. Mitigation: seed.mjs is a single file; the gate fails loudly on any fetch error, and the summary line prints node counts for eyeballing.

## Test plan

Global fixture (`e2e/helpers/console.ts`): every spec file attaches `page.on('console')` and `page.on('pageerror')`, collects SEVERE-level errors, and asserts the collected list is empty in `afterEach` after filtering the allowlist. All tests run against `baseURL http://localhost:5000` with the seeded DB; the seed script is re-run on every gate invocation, so specs assume a fresh deterministic state.

### e2e/specs/auth.spec.ts

- anonymous redirect: `page.goto('/contacts')` lands on the auth page (URL is `/`; `auth-title` "Sign in" visible).
- login success (admin): fill `auth-email`/`auth-password` with `admin@e2e.local`, click `auth-submit`; lands on `/calendar` (promotedRoute) and toolbar shows nav links.
- login failure: wrong password; `auth-error` role=alert banner visible with a message.
- missing fields: submit empty; `auth-error` shows "Enter your email and password." (auth.component.ts:51).
- sign out: after login, click the sign-out button (`getByRole('button', { name: 'Sign out' })`); confirm dialog ("Are You Sure?" prompt-modal) confirms; lands back on the auth page; `/contacts` redirects again.
- admin guard negative: login as `user@e2e.local`; `page.goto('/admin')` redirects away from `/admin` (auth-admin-guard.service.ts:27 NavigateToSignIn).

### e2e/specs/feature-flags.spec.ts

- disabled feature: login; `page.goto('/chat')` shows the feature-disabled page (chat flag seeded false).
- feature-disabled page renders its title/message.
- enabled features pass: `page.goto('/contacts')`, `/calendar`, `/photos` (albums UI because `enablePhotoAlbums` seeded true) all render their pages.
- mutation (restores state): login as admin; `page.goto('/admin/features')`; toggle `feature-toggle-chat` ON; `page.goto('/chat')` renders the chat page; `afterEach` toggles chat back OFF.

### e2e/specs/nav.spec.ts

- logged-out toolbar shows no feature links (mirrors the legacy protractor assertion).
- logged-in toolbar shows links for enabled features and NOT for chat (disabled).
- clicking each toolbar link navigates to the corresponding route.

### e2e/specs/contacts.spec.ts

- list renders the 3 seeded contact names.
- search filters the list by a seeded name substring.
- contact detail: `page.goto('/contacts/<id>')` renders name + email/phone fields (use one seeded id; assert the URL pattern and one field value).
- create contact: login as admin; "add" action opens the form; save a new contact; it appears in the list.
- edit contact: open edit on a seeded contact, change name, save; list shows the new name.
- delete contact: delete a seeded `isEditable` contact; confirm; it disappears from the list (state not restored; this is an accepted mutation since the list test reads seeded names BEFORE this test in file order, and the gate reseeds every run).
- permission negative: `isEditable: false` contact shows no edit/delete actions.

### e2e/specs/calendar.spec.ts

- current month view shows Person A, B, C events (birthdays/anniversary seeded relative to today).
- Person D (3 months ago) is NOT shown in the current month.
- view switch control changes view without console errors.
- printer view opens (calendar-printer) and contains the year.
- event popup/detail shows the person's name.

### e2e/specs/chat.spec.ts

- list renders the 3 seeded messages (author names visible).
- send message: login as `user@e2e.local`; type into `chat-message-input`, click `chat-send`; the message appears in the list.
- edit message: login as admin; edit a seeded message; body updates in the list.
- cross-user visibility: the message sent by `user@e2e.local` is visible when logged in as `other@e2e.local` (same serial run, shared DB).

### e2e/specs/expressions.spec.ts

- list renders the 2 seeded expressions (seed 2 `messageType: 'expression'` records; adjust the seed message count to 5 total: 3 chat messages + 2 expressions).
- create expression: admin creates via the edit card; new expression appears.
- edit expression: change attribution/title; appears updated.
- empty state: search a nonsense string; `no-results-message` renders.

### e2e/specs/photos.spec.ts

- albums grid renders the 2 seeded album titles.
- album detail: open album; the 2 seeded photos render (img loaded from storage emulator URL; assert naturalWidth > 0).
- slideshow: open slideshow for an album; photo-swipe UI renders and next/prev advances the active image.
- upload photo: admin opens album upload dialog, `setInputFiles` with a tiny in-memory PNG buffer; upload completes; the new photo appears in the album (real SDK upload to the storage emulator).

### e2e/specs/people.spec.ts

- list renders the 4 seeded people.
- search/filter narrows the list.
- person detail modal opens and shows name + clan fields.

### e2e/specs/media.spec.ts

- explorer lists the 3 seeded media entries (audio/doc/video titles).
- audio: click the audio entry; player shell renders and the source URL points at `localhost:5000/assets/e2e-fixtures/fixture.wav`; assert `audio.currentTime` advances past 0 within the timeout (WAV is playable in all three browsers).
- video: click the video entry; player shell renders (drive iframe or video element present); do NOT assert playback (external URL, network-dependent).
- doc: click the doc entry; the PDF viewer container renders (ngx-extended-pdf-viewer + pdf.js is cross-browser).

### e2e/specs/admin.spec.ts

- users page lists the 3 seeded users (roles visible for admin).
- create user: admin form creates a user; appears in the list.
- features page renders 9 toggles with correct enabled state (chat OFF, others ON); toggle chat ON then OFF (restores).
- families page lists the 2 seeded families.
- calendars page lists the 1 seeded calendar.
- uploads page lists the pre-seeded approved upload.
- people import: upload a valid JSON buffer (schema read from `src/app/components/admin-people-import/admin-people-import.component.ts` when writing the test); imported person appears in the people list.
- access denial: `user@e2e.local` cannot open `/admin` (already covered in auth.spec.ts; kept here as the permission-check case for the admin domain).

### e2e/specs/public-upload.spec.ts

- unauthenticated access: no login; `page.goto('/upload')` renders the upload form (the one route with no guard).
- happy path: `setInputFiles` on `upload-file-input` with an in-memory PNG buffer + fill required fields; submit; success message; then login as admin and `/admin/uploads` shows the new `pending` upload.
- validation: submit with no file; error state renders (no request sent).
