## 2. Pre-Merge

- Confirm the working tree is clean: `git status`.
- Run the full gate on the branch: `export JAVA_HOME=/opt/homebrew/opt/openjdk@21/libexec/openjdk.jdk/Contents/Home` then `npm run e2e:gate`.
- Push the branch, open a PR to `master`, review the diff, and merge.
- Deploy from `master`. `validate_prod_branch` refuses a production deploy off `master`.
- Pull `master` locally and confirm the release commit is present.

## 3. Environment Contract

- `src/environments/*` is gitignored. Confirm every local environment file, including `environment.prod.ts`, contains `promotedRoutePending: '/photos'`. The code reads it from `environment`, and the gitignored file is not carried by the merge.
- Confirm `src/environments/environment.prod.ts` points at the production Firebase project.
- Confirm `src/environments/build-info.ts` is not staged.
- `deploy.sh` runs `validate_bundle_config` and aborts if the built bundle carries the wrong project domain or database.

## 4. Pre-Deploy Verification

- `npm run e2e:gate` runs inside `deploy.sh` and requires sign-off. Interactive shells approve with input containing `deploy` or `yes`, or a bare `y` or `d`. Non-interactive shells set `E2E_APPROVED=1`, or `E2E_FORCE=1` to override a red gate.
- Never skip a gate that was not actually run. `deploy:*:nogate` is only for a gate already run and passed.
- `npm run test -- --watch=false`, `npm run theme:check`, and `npm run pii:check` should be green in the same tree.
- Confirm the Playwright browsers are installed before trusting a red browser stage: `npx playwright install chromium webkit firefox`.

## 6. Dev Deploy Order

Run dev fully before prod. This verifies rules, functions, the migration, and the seed against a real environment.

1. Merge to `master` and deploy dev normally: `npm run deploy:dev`. This bumps the version, builds, validates, deploys hosting, functions, database rules, and storage rules.
2. UI-013 dev migration. The rules deploy above already removed the `contacts` write. Run the dry run, review the count and byte report, then confirm.
   - `npm run migrate:drop-contacts -- --project lecoursville-dev`
   - `npm run migrate:drop-contacts -- --project lecoursville-dev --confirm --acknowledge-people-source`
   - Confirm `after: records=0`, then run again and confirm `nothing to delete`.
3. UI-008 dev seed, only after license sign-off:
   - Plan: `npm run seed:dev`
   - Apply: `npm run seed:dev -- --confirm`
   - Optional clean: `npm run seed:dev -- --clean --confirm`
   - The seed refuses any project other than `lecoursville-dev`.
4. UI-005 data rights. No data action. Open the footer and submit one test request, then resolve it in `/admin/data-requests`.
5. Verify the dev surfaces listed in section 8.

## 7. Production Deploy Order

1. Confirm the pre-merge gate, human sign-offs, environment contract, and clean tree.
2. Decisions before the destructive step: take a prod backup export for UI-013 if required. The deleted `contacts` node is not restorable from the repo.
3. Deploy production normally: `npm run deploy:prod` with sign-off. This bumps the version, commits `Release <version>`, builds, validates the bundle, deploys hosting, functions, database rules, and storage rules, then creates and pushes the release tag.
4. UI-013 prod migration, only after the rules and code that stop writes are live:
   - `npm run migrate:drop-contacts -- --project lecoursville`
   - Review the dry run, then `npm run migrate:drop-contacts -- --project lecoursville --confirm --acknowledge-people-source`
   - Confirm `after: records=0` and a no-op second run.
5. UI-008 is dev only. Never run the dev seed against production.
6. UI-005 hard deletes run only from the operator script after a request is verified and granted, never automatically:
   - `node scripts/migrations/delete-data-request-subject.mjs --project lecoursville --request <id> --target <path> --export <file> --confirm`
   - The script refuses without `--confirm`, writes the export first, deletes only an allowlisted target, and writes a non-PII audit entry.

## 8. Critical Ordering

- Deploy the code and rules that remove contact writes before running the contacts migration. The migration refuses while any contacts write grant exists in the deployed rules.
- Deploy functions with the Node 24 runtime in the same release so the auth and data-rights triggers exist before the UI that calls them.
- Deploy the `messages` read tightening with or before the open signup UI. Do not leave a window where open signup exists without the approved-only read rule.
- Deploy the `dataRequests` rules before enabling the footer. The footer ships in the same bundle, so a normal deploy satisfies this.
- Prod is always after dev.

## 10. Rollback

- Code: revert the release commit or deploy the prior tag.
- Rules: restore the prior snapshot from `database-rules/2026-11-08/before.json` and redeploy database rules.
- Feature flags: turn off `legacyCalendarPdf` or `enablePhotoAlbums` if a surface misbehaves. Both default off.
- Hard deletes are irreversible. The pre-delete export is the only recovery path.
- The `contacts` node deletion is irreversible. The prod backup export or the dry-run report is the only safety record.
