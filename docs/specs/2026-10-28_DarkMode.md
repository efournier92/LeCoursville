# Dark Mode

Branch: `dark-mode` worktree at `/Users/e/mnt/bnk/cs/lecoursville-dark`, based on commit `51fd8cdb`.

## Context & Motivation

LeCoursville ships a single light visual language built on custom properties in `src/styles.scss` plus a Material 3 light theme. Users have no way to view the app in dark mode, and roughly 153 hardcoded color literals scattered across the global sheet and component SCSS files mean any theming attempt today would miss large parts of the UI. This spec adds a binary per-user light/dark theme toggle backed by RTDB, and does the full color sweep and token consolidation required to make dark mode actually cover the whole app rather than a partial overlay.

## Glossary

- **Theme**: the binary per-user visual mode, stored as `'light'` or `'dark'` at `users/{uid}/prefs/theme`. Light is the default for every user without a stored value.
- **Token**: a CSS custom property defined in the `html` block of `src/styles.scss` (for example `--color-surface`), the only sanctioned way to reference a color in app styles.
- **Dark selector**: the `html[data-theme="dark"]` attribute selector under which all dark token overrides and the dark Material theme are scoped.

See also `docs/GLOSSARY.md` for existing domain terms.

## Goals

1. Binary theme toggle, light (default) or dark, stored as `'light'|'dark'` at `users/{uid}/prefs/theme` in RTDB.
2. Users with no stored value get LIGHT; `prefers-color-scheme` is explicitly ignored.
3. Toggle control in the root toolbar near the sign-out area, visible to signed-in users only; guest/unauthenticated pages render light.
4. Mechanism: `html[data-theme="dark"]` set by an Angular theme service; dark token override block re-derives all custom properties; a second `mat.define-theme` with `theme-type: dark` plus a conditional `@include mat.all-component-themes($dark-theme)` scoped under the dark selector; all hardcoded `#ffffff` Material overrides switch on the same selector or consume tokens.
5. Full color sweep: every hardcoded hex/rgb literal in `src/styles.scss` and component SCSS is audited and, where it is a duplicate or near-duplicate of a token semantic, consolidated into the shared token vocabulary. New tokens only where no existing token fits.
6. Theme applies as soon as the user node resolves; initial render is light and switches on resolve (flash accepted, see risks). Toggle writes RTDB and applies locally immediately. No localStorage for the theme value.
7. E2E coverage in a new `e2e/specs/dark-mode.spec.ts` with exactly the seven cases listed in the Test Plan.
8. WCAG AA contrast (4.5:1 body, 3:1 large text) in both modes for text on surface, card, and toolbar backgrounds.

## User Stories

1. As a signed-in user, I can toggle dark mode from the root toolbar so the entire app, including Material overlays, renders in dark colors.
2. As a signed-in user, my theme choice persists across sessions and devices, because it is stored on my user node in RTDB.
3. As a user who has never chosen a theme, I see the light theme regardless of my OS setting.
4. As a guest on an unauthenticated page, I always see the light theme.
5. As a user toggling the theme, the new theme applies immediately without a reload.

## Non-Goals

- No redesign or visual overhaul beyond re-derived token values.
- No follow-system (`prefers-color-scheme`) mode, now or as a hidden third state.
- No per-component Material overrides beyond switching the existing override blocks on the dark selector.
- No localStorage cache of the theme value.
- No changes to feature behavior; this is presentation only.
- No admin UI for managing other users' themes.

## Design Principles

1. Tokens are the only color vocabulary: after the sweep, app SCSS references tokens (or component-local values derived from tokens), never raw hex, except documented exceptions (photos under `assets/`, chart-specific accents get their own tokens rather than raw hex).
2. One theme service, one source of truth: a single `ThemeService` owns read, apply, and write of the theme; no component reads `prefs/theme` directly.
3. Light is the floor: every unknown state (no user, unresolved auth, missing prefs) renders light.
4. Minimal storage surface: one string field on the user node; no new top-level RTDB nodes.

## Backend / Data Requirements

- **Schema**: `users/{uid}/prefs/theme` = `'light'` | `'dark'`. Written only by the owning user via the existing client write path.
- **Write path**: `ThemeService.setTheme(theme)` composes the current `AuthService.user` with `prefs: { theme }` and calls the existing `AuthService.updateUser` (`src/app/services/auth.service.ts:155-160`), which performs `rtdb.object(users/{user.id}).update(user)`. No new service writes to RTDB.
- **Read path**: `ThemeService` subscribes to the user stream already published by `AuthService` (fed by the `users/{uid}` `valueChanges()` at `src/app/services/auth.service.ts:133`). When a user object with `prefs.theme === 'dark'` arrives, it applies the dark attribute; when the user object has no `prefs` or `prefs.theme !== 'dark'`, it removes it.
- **RTDB rules impact**: none, no change to `database.rules.json`. The whole-node self-write disjunct at `database.rules.json:158` permits `$uid === auth.uid` updates that preserve `email`, `roles/user`, `roles/admin`, and `roles/super`; `prefs/theme` is additional data on the same node and rides through unchanged. Note the predicate also requires `newData.child('email').val() === data.child('email').val()`, so the theme write must send the full existing user object (which `updateUser(user)` already does given the current in-memory user), not a partial `{ prefs }` patch against the node path.
- **Cloud functions**: no changes. Nothing server-side reads the theme.
- **Seed**: `scripts/e2e/seed.mjs` is NOT modified; seeded users have no `prefs` node and exercise the light fallback.

## Frontend / UI Requirements

### ThemeService

New `src/app/services/theme.service.ts`:

- `theme$: Observable<'light' | 'dark'>` derived from `AuthService.user$`.
- `toggle()`: computes the next theme, applies it to the DOM immediately (optimistic), and calls `AuthService.updateUser` with the updated user object.
- Apply = `document.documentElement.setAttribute('data-theme', 'dark')` or `removeAttribute('data-theme')`.
- On sign-out / null user: remove the attribute (guest is always light).
- Injectable, provided in root app config like other services.

### Toggle control

- A `mat-icon-button` in the root toolbar's `icons-menu` area (`src/app/app.component.html:22-77`), rendered only in the signed-in branch (`@else` block at `:40-76`), adjacent to the sign-out entry point.
- Icon: `dark_mode` when current theme is light, `light_mode` when dark; `aria-label` "Switch to dark mode" / "Switch to light mode"; `data-testid="theme-toggle"` and `data-testid="theme-state-{light|dark}"` for e2e targeting.
- No dialog, no confirm: single click toggles.

### Material dark theme

After the light `$theme` (`src/styles.scss:121-134`), define:

```scss
$dark-theme: mat.define-theme(
  (
    color: (
      theme-type: dark,
      primary: mat.$green-palette,
      tertiary: mat.$orange-palette,
    ),
    typography: (plain-family: var(--font-body), brand-family: var(--font-display)),
    density: (scale: 0),
  )
);
```

Emit conditionally: the existing `html { @include mat.all-component-themes($theme); ... }` block at `src/styles.scss:136-161` keeps light as the default, and a parallel `html[data-theme="dark"] { @include mat.all-component-colors($dark-theme); ... }` block re-issues the component color overrides (use `all-component-colors`, not the full `all-component-themes`, to avoid re-emitting typography/density; if the Angular Material version in use lacks that mixin, `all-component-themes` under the selector is acceptable and produces only duplicate CSS weight). The hardcoded white overrides must become theme-aware:

- Toolbar (`:140-143`): keep brand green container; text stays white in both modes (green toolbar is identical across themes), so `#ffffff` here may remain but should switch to a token `--color-on-brand` set to `#ffffff` in both blocks.
- Select panel `:147`, menu `:148`, datepicker `:149`, autocomplete `:150`, dialog `:152`: replace `#ffffff` with `var(--color-surface)` so they follow the active theme with no selector duplication.
- Form-field overrides `:157-160`: unchanged.

## Production Risks & Mitigations

- **Flash of light theme (FOUC-adjacent)**: initial render is light and flips when the user node resolves. Accepted by locked decision; mitigation is that the toggle applies optimistically and `AuthService` already streams the user before most pages paint, keeping the flash to sub-second on warm connections. Not solved with localStorage (locked out).
- **Missed literals**: a stray hardcoded white renders as glare in dark mode. Mitigation: the sweep checklist in Summary Of Changes plus a review grep for `#[0-9a-fA-F]{3,8}` and `rgb(` across `src/` as a verification step.
- **RTDB write shape**: the rules predicate requires email and roles preserved; a partial `{ prefs }` write would be rejected. Mitigation: writes go through `AuthService.updateUser` with the full current user object.
- **Offline/rejected write**: optimistic local apply leaves DOM dark while RTDB write fails; next user-node emission reconciles. Accepted; the stream is the source of truth.
- **Contrast regressions**: brand green `#2D5A27` on dark backgrounds fails AA for text; the dark palette table gives every brand token a lightened dark variant, and the Test Plan does not gate contrast computationally (manual verification step below).
- **Bundle size**: a second component-color emission adds CSS weight; bounded and accepted.

## Test Plan

New `e2e/specs/dark-mode.spec.ts`. Import `test` from `e2e/helpers/fixture.ts` (console-error collector). Sign in via `login(page, 'user')` from `e2e/helpers/auth.ts`. Cases, exactly:

1. **Fresh user default light**: sign in as `user` (no prefs node), assert `html` has no `data-theme="dark"` attribute and no `.theme-dark` class, and body background equals the light token value (`#F3F4F6`).
2. **Toggle on**: click `data-testid="theme-toggle"`, assert `html[data-theme="dark"]` present, computed `color-scheme` is `dark`, and body/surface background changes from the light value.
3. **Persist across reload**: while dark, `page.reload()`, re-authenticate if redirected, assert dark attribute re-applied after user node resolves.
4. **Toggle off restores light**: click toggle again, assert attribute removed and light background back; reload and assert still light.
5. **Guest never dark**: while signed-in user is dark, sign out, assert auth page renders with no dark attribute and light background.
6. **RTDB write lands**: after toggling on, `readDb(\`users/${uid}/prefs/theme\`)` from `e2e/helpers/admin-db.ts` returns `'dark'`.
7. **No console errors** in any of the above (fixture collector asserts empty on each case).

Gate: `npm run e2e:gate` (full Chromium + WebKit + Firefox matrix).

Manual contrast verification: sample toolbar text on brand green, body text on `--color-app-bg` and `--color-surface`, and link color on surface, in both modes, against WCAG AA (4.5:1 body, 3:1 large).
