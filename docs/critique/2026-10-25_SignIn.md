### Notes On C-20261025-02

- The icon font is bundled at `src/assets/fonts/MaterialIcons-Regular.woff2` (Material Icons, 2,233 ligatures). Glyph names below were checked against the font's GSUB ligature table.
- Available emergency glyphs: `sos`, `emergency`, `crisis_alert`, `contact_emergency`, `warning`, `report`, `announcement`, `error`.
- Unavailable in the bundled font: `e911_emergency`, `health_and_safety`, `local_hospital`, `medical_services`, `notification_important`. Do not pick these unless the batch adds a font.

### Notes On C-20261025-03

- External sources were spot-checked on 2026-10-25. GitHub's sign-in page keeps `Forgot password?` visible beside the password field and puts `Contact GitHub Support` in the page footer, not in the form. The OWASP Authentication Cheat Sheet recommends generic credential errors, a neutral reset response (`If that email address is in our database...`), and deferring CAPTCHA to `a small number of failed login attempts`.
- NIST SP 800-63B-4 requires redress mechanisms to be `easy for subscribers to find and use`, which argues against removing the human-help route entirely. The quiet discovery link below is the compromise.
- No source found a precise numeric threshold for revealing a help route. GOV.UK cites 5 to 10 failed attempts for lockout or extra checks, and OWASP says a `small number`. The owner chose the threshold of 1, which is a UX threshold for revealing help, not a security lockout.
- Owner decision on 2026-10-25: reveal after a single failed credential attempt. The critic preferred 2 to absorb typos and password-manager misses, so the mitigation is to keep the reveal quiet and additive rather than a modal or a focus jump.
- Pattern verified in the repo: `onSignIn` clears both `error` and `info` on every attempt (`auth.component.ts:84`), so reveal state cannot be derived from either banner. It needs its own flag.
- Security constraint: `mapAuthError` merges `auth/user-not-found`, `auth/wrong-password`, and `auth/invalid-credential` into one string (`auth.component.ts:165` to `:170`). The reveal must key on the mapped message and the attempt count, never on the raw Firebase code, or the UI becomes an account-existence oracle again.
- Routing research: the Google redirect path returns on a fresh page load (`auth.component.ts:52`), so an in-memory attempt counter is empty on exactly the error that most needs help. Use `sessionStorage`, which survives the redirect in the same tab and dies on tab close. The repo already uses it at `src/app/services/media-upload.service.ts:564`.
- Admin cost: every `Get help signing in` submit writes a recovery request and fans out an admin alert email (`functions/src/submit-recovery-request.ts:197`). Defaulting the button to hidden also cuts honest accidental queue volume.

Proposed default state.

- Keep the email field, password field, primary `Sign In` button, Google button, and `Forgot Password?`.
- Replace the full escalation block with one quiet text link, `Trouble Signing In?`, in a footer outside the card.
- Clicking that link expands the block in place inside the card, with the label `Locked Out Of Your Account?` and the `Get Help Signing In` button.
- Hide the footer link once the block is visible, so the page never shows two help affordances at once.

Placement constraint: `.auth-page` is a single-child flex row (`src/app/components/auth/auth.component.scss:1`), so a footer outside the card needs a column wrapper or a bottom-anchored element. Keep the card's top alignment, the existing mobile padding, and a target size of at least 24 by 24 CSS px for the link.

Proposed reveal triggers.

| Trigger | Reveal | Copy |
|---|---|---|
| Page load, nothing typed | No | footer link only |
| Missing fields or `auth/invalid-email` | No | current validation copy |
| First failed credential attempt in the session | Yes | `Incorrect Email Or Password.` plus `Locked Out Of Your Account?`, `Get Help Signing In` |
| `auth/too-many-requests` | Yes, immediately | `Too Many Attempts, Try Again In A Minute.` plus the block |
| Forgot Password clicked with no email | No | `Enter Your Email First.` |
| Reset request completed, info banner shown | Yes, label variant | `Tried A Reset And Still Locked Out?` |
| `auth/account-exists-with-different-credential` on redirect return | Yes | current message plus `Locked Out Of Your Account?` |
| `auth/popup-blocked`, `auth/popup-closed-by-user`, network error, unknown | No | banner only |

Implementation notes for the batch.

- State: add `helpRevealed` and `helpTrigger` fields, persisted as `auth.helpRevealed` and `auth.helpTrigger` in `sessionStorage`. A counter is no longer needed for the threshold, because one failure reveals help; keep one only if the `auth_sign_in_failed` event needs an attempt number. Clear both on a successful sign-in.
- Never hide the block again within the session after it is revealed. Clearing the form must not un-reveal it.
- Reveal is additive, not a layout swap that moves the submit button. Keep DOM order after the error banner so keyboard order stays predictable.
- Accessibility: give the revealed block `role="region"` and `aria-label="Get Help Signing In"`, and announce it without moving focus away from the form. The error banner already has `role="alert"`.
- Analytics: add `auth_sign_in_failed { reason }` (add `attempt` only if a counter is kept), `auth_help_revealed { trigger }`, and pass `trigger` into the existing `recovery_opened` event at `auth.component.ts:141`.
- Tests: assert the footer `Trouble Signing In?` control is visible by default while the `Get Help Signing In` block is absent. Keep the two accessible names distinct so role queries cannot match both.
- Tests: `e2e/specs/account-recovery.spec.ts:126` asserts the button is visible on load and `:129` asserts its text. `addRecoveryRequest` at `:107` clicks the button immediately after `page.goto('/')` and is reused by five tests. The batch must assert absence by default, reveal help after one deterministic failed submit, and rewrite the helper to trip the trigger first. Do not depend on emulator rate limiting for `too-many-requests`.

Decided on 2026-10-25.

- Reveal after a single failed credential attempt.
- Keep a quiet discovery link labeled `Trouble Signing In?`, placed in a footer outside the card.
- Implement the discovery control as a button styled as a text link, because it reveals content in place rather than navigating.

Open decisions for the owner.

1. Whether a Forgot Password click alone should reveal the block, or only a completed reset request.
2. Label variants: one neutral `Locked Out Of Your Account?` everywhere, or the per-trigger variant above.

### Notes On C-20261025-04

- Diagnosed 2026-10-25 against `lecoursville-dev`. IAM read from the Cloud Run Admin API: `requestpasswordreset`, `submitrecoveryrequest`, `admingenerateresetlink`, `closerecoveryrequest`, and `updatealertrecipients` have no bindings at all. `claimmemberrole` and `createmediaupload` hold `roles/run.invoker` for `allUsers`.
- Browser symptom is misleading by construction: Cloud Run answers `403` with an HTML body and no CORS headers, so the only thing the browser can report is a CORS failure.
- The e2e gate cannot reproduce it. The emulator serves functions from `127.0.0.1:5001`, where no Cloud Run or IAM layer exists.
- Production answers `404` for every function name today, so production has no deployed functions and the same failure will appear there only after a functions deploy.
- Fix is a five-service IAM repair plus a post-deploy preflight probe wired into `scripts/deploy.sh`. Full detail in `docs/specs/2026-10-25_CallableInvokerAndRecoverySpacing.md`.
